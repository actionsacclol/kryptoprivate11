You are building **Fable Sniper**, a production-minded, Solana-first memecoin launch monitoring and automated trading application.

This is not a toy script and not a blind “buy every new token” bot. The goal is to create a well-structured foundation for a low-latency launch-detection, token-risk-analysis, strategy-testing, and execution system that can eventually support Pump.fun, PumpSwap, Raydium, Meteora, Bonk.fun, Jupiter, and other Solana venues.

The first version must prioritize:

1. Correctness.
2. Safety.
3. Observability.
4. Replayability.
5. Modular protocol support.
6. Paper trading before live trading.
7. Explainable strategy decisions.
8. Fail-closed behavior when data is unknown or outdated.

Do not claim profitability. Do not implement sandwich attacks, front-running of specific users, market manipulation, wash trading, spoofing, or any system intended to harm other traders.

## Primary objective

Create a strong first working version that:

* Connects to Solana.
* Detects new Pump.fun launches directly from on-chain activity.
* Decodes supported Pump.fun events and accounts.
* Performs local token and creator risk checks.
* Tracks early buys, sells, holders, and bonding-curve activity.
* Calculates an explainable launch score.
* Runs in paper-trading and shadow modes.
* Records raw and decoded events for replay.
* Includes a modular execution interface, but keeps real-money trading disabled by default.
* Provides a clean desktop dashboard for monitoring launches and decisions.

Do not attempt to implement every launchpad in the first pass. Build the architecture so additional protocol adapters can be added cleanly.

## Preferred technology stack

Use:

* Rust for the core engine.
* Tokio for asynchronous tasks.
* Tauri or Electron only for the desktop shell, with preference for Electron if integration is more straightforward.
* React.
* TypeScript.
* Vite.
* SQLite for initial local storage.
* SQLx for Rust database access.
* Serde for serialization.

* Reqwest for HTTP.
* Solana Rust SDK crates where appropriate.
* Native Solana WebSocket subscriptions for the free development feed.
* A provider abstraction that can later support Yellowstone gRPC.
* Vitest for frontend testing.
* Rust unit and integration tests for the engine.

Keep all signing, strategy execution, event decoding, wallet handling, and risk analysis in the Rust engine. The frontend must not be part of the latency-sensitive execution path.

## Important implementation rule

Before writing protocol-specific decoding logic, research and verify the current official sources.

Use current official documentation and repositories wherever possible:

* Solana RPC and WebSocket documentation.
* Pump.fun public documentation and current IDLs.
* Pump.fun and PumpSwap program details.
* Yellowstone gRPC documentation.
* Raydium SDK V2.
* Meteora SDKs.
* Jupiter swap documentation.
* Jito transaction and bundle documentation.

Do not copy random GitHub bot code without reviewing it.

When using a community repository:

* Inspect its license.
* Inspect its dependencies.
* Verify account layouts against current official IDLs.
* Check for outdated program IDs.
* Check for hidden outbound requests.
* Check for wallet or key logging.
* Check for hardcoded fee-recipient addresses.
* Check whether returned transactions contain unexpected instructions.

Create a `RESEARCH.md` file documenting:

* Current account layouts.
* Repository licenses.
* Information that still requires verification.
* Assumptions made during implementation.

Do not guess account layouts. If a current layout cannot be verified, create a clearly labeled stub and fail closed.
