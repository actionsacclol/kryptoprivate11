# API, rate-limit and capacity swarm (2026-09-09)

Six researchers in parallel over everything the app asks of somebody else's
server: Solana RPC, EVM RPC on two chains, market-data providers, request
efficiency, failover behaviour, live feeds, and the terms that decide what a
shipped desktop app is allowed to do.

The brief carried one rule above coverage: **never invent a number.** Every
limit had to carry a primary-source URL the researcher actually fetched or a
response header they actually observed, or be marked UNVERIFIED. That rule
earned its keep — it produced one refutation that would otherwise have cut a
provider to a third of its real capacity, and it is why the tables below can be
coded against.

Everything was read-only. No account was created, no key was used, and no
endpoint was stress-tested to find its ceiling.

Raw per-dimension reports: `scratchpad/api/results/{rpc-sol,rpc-evm,market,efficiency,failover,feeds,inventory}.md`.

---

## 1. The one pattern behind five P1s

**A refusal that does not look like a refusal defeats every piece of machinery
built to handle refusals.**

The 2026-09-06 rate-limit swarm built a good park: escalating backoff, honoured
`Retry-After`, strike decay, a queue-wait cap, a priority lane. All of it hangs
off recognising that a provider said no. Five separate findings, from four
independent researchers, are the same bug in different clothes:

| Where | The refusal arrives as | What the app does |
| --- | --- | --- |
| GeckoTerminal | HTTP **200** with a JSON error body | Takes the success path, and **deletes an existing park** |
| Solana RPC | JSON-RPC error, no HTTP status | No park, no failover — 60 calls in 2 s proved it |
| Solana RPC | Cloudflare **403** challenge | Misread as a bad API key; host banned 15 min, user told to replace a working key |
| Ankr (EVM) | HTTP **200** auth error | Invisible to the rejection logic |
| LeoRPC (EVM) | `-32603` inside HTTP **200** | The failover ladder accepts it as success |

`electron/data/http.ts:471` branches on `res.ok` alone. Everything that
recognises throttling — `park()`, the `Retry-After` read, the escalation, the
body cancel — lives inside that one `!res.ok` block. Then line 499 makes it
worse:

```ts
// A success clears any lingering park — unless the provider's own
// counters say the next call would be the one refused.
blockedUntil.delete(id);
```

So a polite refusal does not merely fail to park a provider. It reaches the
success path and **un-parks** one that an earlier honest 429 had correctly
parked.

**The fix is one hook.** A per-provider response validator that runs *before*
the `res.ok` branch, letting a provider declare "this 200 is actually a
refusal" and routing it into `park()` like any 429. The same hook covers the
JSON-RPC cases on both rails. One change, five findings.

## 2. Verified limits

Numbers I confirmed personally are marked **[C]**; the rest carry the
researcher's evidence class. `OBSERVED` = a response they quote. `DOC` = a
primary source with its date.

### Solana public RPC — meters PER METHOD, and publishes it

`api.mainnet-beta.solana.com` returns a full `x-ratelimit-*` set on every
reply. **[C]** — my own probe, cold IP:

```
x-ratelimit-tier: free
x-ratelimit-method-limit: 150      (getHealth)
x-ratelimit-rps-limit: 250
x-ratelimit-endpoint-limit: unlimited
x-ratelimit-conn-limit: 40
x-ratelimit-connrate-limit: 40
```

| Method | Budget | The app's limiter allows |
| --- | --- | --- |
| `getBalance`, `getHealth`, `getTokenSupply` | 150 | 40 — **30× too slow** |
| `getLatestBlockhash` | 100 | 40 |
| `getAccountInfo`, `getMultipleAccounts` | 50 | 40 |
| `getSignatureStatuses` | **10** | 40 — **4× over** |
| `getSignaturesForAddress` | **10** | 40 — **4× over** |
| `getTokenAccountsByOwner` | **10** | 40 — **4× over** |
| `getTokenLargestAccounts` | **0** | always 429 |

The global ceiling is **250 rps**, not the 100-per-10-s the docs state. So the
app is badly over-throttled overall and over-spending on exactly the three
methods the trade path, the template learner and the portfolio hammer.

`grep -c x-ratelimit`: `http.ts` 5, `rpcClient.ts` **0**. The provider layer
already parks from these headers. The RPC layer, the one being metered per
method, reads none of them.

### GeckoTerminal — 30/min, and the "10" is a different product

**REFUTED cross-dimension claim.** Two researchers surfaced a contradiction;
resolving it matters because the wrong answer would have throttled a working
provider to a third of its capacity.

| Source | Says | Product |
| --- | --- | --- |
| `apiguide.geckoterminal.com/faq` | "The current rate limit for the Public API is set at 30 calls per minute." | The public API at `api.geckoterminal.com` — **what this app uses** |
| `geckoterminal.com/dex-api` | "from 10 calls/min to 250 calls/min" | Marketing for paid **CoinGecko Pro on-chain**, a different host |

`MIN_GAP_MS.geckoterminal = 2_100` with a 28/60 s window is **correct — do not
lower it.** But the per-minute figure is not the binding constraint: real
refusals were observed, and a code comment records a 429 after four burst
calls. The 2.1 s gap is doing the real work.

> **A note for anyone reading the raw reports.** Two separate researchers, and
> later the EVM fix lane, each independently reported GeckoTerminal as
> "documented 10/min" and recommended lowering the app's 28/min budget. That is
> wrong — see the refutation above. The claim keeps recurring because the
> marketing page ranks well and reads authoritatively. The app's budget is
> correct; do not act on that recommendation if you meet it again.

### BNB — no single free endpoint does everything

`chains.ts` models BNB as if one nearly does. Probed 28 endpoints:

| Family | Receipts | Logs | `eth_simulateV1` | State window |
| --- | --- | --- | --- | --- |
| Official dataseeds (`*.bnbchain.org`, defibit, ninicoin, NodeReal) | yes | **none** (`-32005`, disabled per BNB's own docs) | yes | ~110 blocks ≈ 50 s |
| publicnode — **the app's default** | **none, at any depth** | near head | yes | ≤20 blocks |
| `rpc-bnb.blockmachine.io`, NodeReal shared-key | yes, archival | yes, archival | **no** | deep |

### Robinhood Chain 4663 — better than assumed

The official RPC serves 200,000-block log windows, archive receipts and
`eth_simulateV1`, but prunes state at roughly 4,096–16,384 blocks (7–27 min).
There are **three** live keyless endpoints, not one: `robinhood-rpc.publicnode.com`
(serves receipts by hash a million blocks back, unlike its BSC twin) and
`rpc.ordofi.network` (state 1M blocks deep). Alchemy, Chainstack and QuickNode
all support the chain. Both alternates offer WSS; the official RPC does not.

### The pubsub header means connections, not subscriptions

`x-ratelimit-pubsub-limit: 10` is **10 pubsub connections per IP**, not 10
subscriptions per socket. Proven three ways: the header decrements per
connection, 16 `logsSubscribe` on a single socket all acked, and connections
11–13 got HTTP 429 at the handshake.

Both `electron/engine/priorityFeed.ts:286` and
`electron/engine/walletWatcher.ts:44` encode the wrong reading as
`PUBLIC_SUB_CAP = 10`, with a comment stating "caps subscriptions at 10 per
connection". A user following 14 copy leaders gets **4 silently unwatched** and
is told to buy a Helius key for a limit that does not exist.

The flip side is worse: worst-case connection count on `api.mainnet-beta` is
**exactly 10 of 10** — feed, pAMM tape, priority feed, wallet watcher, confirm
socket, three DBC pools, LaunchLab, Boop. The 11th dial 429s, and every socket
class routes that into a 30 s park on the whole host. There is no
`powerMonitor` handling anywhere, so a laptop lid opening is an unmanaged
stampede into that cap.

## 3. The user's actual question: other free APIs to pull from

**The honest answer is a reframe.** Of twelve providers researched as new, ten
are noise — key-gated, curated-listings only, or barred by their own terms
(DefiLlama §8.10 forbids commercial use; Bitquery free is "technical
development" only; Solscan's keyless tier is dead and its terms say personal
use only). There is essentially no undiscovered free keyless API that fills a
gap this app has.

What the research found instead is worth more than a new provider.

**Capacity we already own and do not use:**

- **GeckoTerminal `/tokens/{addr}/info`** is already wired in the repo but
  called *only* from `evm/market.ts:167`, never on Solana. Keyless, it serves
  holder count, top-10 concentration, mint/freeze authority, dev holding % and
  a honeypot flag. On a minutes-old mint the authorities are populated while
  `holders.count` is honestly null. **This contradicts the standing "holder
  features need a Helius key" note.**
- **DexScreener `/tokens/v1/solana/{≤30}`** returns byte-identical pair objects
  to the per-mint route — about a 30× saving on the portfolio path. It
  silently drops tokens past 30, so the cap must be enforced client-side.
- **GeckoTerminal `simple/token_price`** with `include_*` flags returns price,
  market cap, 24 h volume, 24 h change and liquidity for 30 tokens in one call.
- **`getMultipleAccounts`** (budget 50) instead of 60 individual
  `getAccountInfo` (budget 50, spent one at a time).
- **Jupiter's batched `audit.devMints`** is already on every Discover row, from
  a call already made. See §4.

**Genuinely worth adding:**

- **Alchemy** — the largest free allowance for this workload (30M compute units
  a month), serves every method the app needs including the holder lookups the
  public endpoint refuses outright.
- **Solana Tracker** (BYO key) — the only provider outside Birdeye serving LP
  burn and sub-second candles, at 3 rps vs Birdeye's 1, and the only terms that
  affirmatively permit displaying derived data. Related: **Birdeye's free tier
  does not expose mint/freeze authority or LP data at all**, so Settings
  currently mis-sells it as the safety upgrade.
- **BNB `wss://bsc-rpc.publicnode.com`** — works keyless, measured. The EVM
  rails have zero sockets today.
- **PumpPortal's WebSocket** — keyless, 1.2 MB/h.

**Dead ends, so nobody re-checks them:** dRPC has dropped Solana from free;
Ankr's keyless endpoint 403s everything; OMNIA 521s; BlockEden 402s; Helius
webhooks need a public HTTPS endpoint and are structurally unusable for a
desktop app; `transactionSubscribe` is Developer-tier; Jupiter, DexScreener and
Binance streams returned 404/403/451.

**On paid tiers, the expectation inverts.** Holder analysis needs a *key*, not
a *plan* — Alchemy's and Helius's free tiers both serve it at zero cost. What
genuinely costs money is the firehose socket: at 20 credits/MB even Helius
Developer at $49 buys roughly 12 days of it.

## 4. Waste, measured

Every number here came from a harness that bundled the real modules and counted
requests against a stubbed `fetch`.

**Idle Discover, four columns, default settings, nobody touching anything:
230 HTTP calls/min — of which 89/min go to pump.fun against its documented 60
per 60 s.** The app is ~48% over a published limit while sitting still.

- **pump.fun is paid twice for what it already sent.** The `/coins?` list route
  returns complete records; `coinForIntel` then buys each row back
  individually — 45/min measured, 100% of them following a list read that
  contained the row.
- **A per-row creator history costs another 38/min** on the same 55/min window
  Discover's own feeds compete for, and it visibly starves them: making
  creators unique took the New column from 10/min back to its configured
  18/min.
  **[C] Why it is redundant:** `shared/launchintel.ts:368 CreatorHistory` does
  not declare `devMints`, which is why `launchIntel.ts:349` widens its own
  parameter with `(CreatorHistory & { devMints?: number | null })` to reach it.
  A type widened at the call site to reach a field the type lacks is the tell —
  the branch is dead. Meanwhile `devMints` is real and populated on a *different
  object*: `providers/jupiter.ts:175` sets `s.audit.devMints` from a batched
  response already on every row.
- **A 60-mint portfolio build makes 208 requests in 15.6 s** — 60 individual
  DexScreener, 60 individual pump.fun, 60 individual `getAccountInfo`.
  `summaryMany` batches only the Jupiter third. Worse, `TTL_TOKEN = 8 s` is
  shorter than the assembly it warms, so **26 of the 60 mints re-fetched the
  Jupiter row the same function had just batched**.
- **Discover has a route gate but no visibility gate**, so all 230 calls/min
  continue while the window is minimised, on the route the app opens on.
- **The priority and normal lanes fire in lockstep pairs** — 11 of 22 measured
  gaps were 0 ms, 60 req/min against a 28/min budget. The app manufactures its
  own parks. Priority traffic into a parked host escalates the park to 120 s
  for everyone else, and routine chart loads are marked priority.
- **The EVM rail fires up to 30 concurrent priority DexScreener calls** that
  bypass the park and re-extend it — the 2026-09-06 A4 failure reintroduced on
  a different rail.
- `onchain.topHolders` is unmemoised and runs 3× per token page on
  `getTokenLargestAccounts`, the one method the public RPC refuses hardest.
- The portfolio prices wSOL with a 4-call `market.summary()` for a number
  `jup.solUsd()` already caches.

## 5. Correctness, not just capacity

These cost the user money rather than quota.

**[C] An unreadable mint scores SAFE.** Three lines in three files:

```ts
onchain.ts:84   if (!res.data) return { ...UNCHECKED('mint account not found'), checked: true };
market.ts:505   mintAuthority: facts.checked ? facts.mintAuthority !== null : null,
market.ts:1212  verdict: !m.checked ? null : m.mintAuthority === false ? 'pass' : …
```

`UNCHECKED` sets both authorities null; the branch then overrides the one field
that protects the user. Downstream, `checked: true` plus a null authority reads
as a positively-observed absence, and the honest-null guard (`!m.checked`) has
already been defeated. So "the RPC could not find this mint" renders as **"Mint
authority: Disabled. No new supply can be minted."**, sourced `onchain`, on the
two heaviest security gates (weights 14 and 16). In SPL a null authority
genuinely *is* the safe state, which is why the conflation is easy to miss —
but only when the account was actually read. Reachable from a lagging node on a
seconds-old mint, which is exactly when this app is used.

**The token page asserts market facts it never observed.** With every price and
pool source parked, `market.ts:1182 tokenDetail()` shows "No trading pool
found — this token may not be tradeable yet" and "No provider returned a
price", next to a Buy button — while `parkNote()` in the same file already
returns a sentence naming all five parked providers.

**A doomed holder lookup blinds every other RPC read.** `getTokenLargestAccounts`
has budget 0 and returns `retry-after: 10` on the first call **[C]**.
`rpcClient.ts:178 noteRateLimit` keys the park by **host**, not host+method, and
`PARK_MAX_MS` is 10 s — so the maximum park is reached on the first strike,
blocking balances, blockhash, account info and fill detection. Strike decay is
60 s, so browsing token pages keeps it pinned. The user-facing message is
already honest; the collateral damage is the bug.

**Unaged remembered prices drive actions.** `lastKnownPriceSol` and
`tape.lastPriceSol` reach paper fills, percentage-order anchors, fee billing
and script rules with no age check.

**BNB fills are priced from a state window narrower than the receipt timeout.**
`ledger.ts:238` reads `getBalance` at `bn-1`/`bn` through dataseed, whose state
window bisected to 110–119 blocks ≈ **50 s**, against a 60 s receipt timeout.

**Every BNB broadcast goes through publicnode**, which states "MEV protection
enabled by default" — sends bypass the public mempool, undocumented in the
config.

**The BNB launch index is capped at ~67 minutes by the endpoint, not the
chain.** blockmachine served 5,000-block log windows at depth 1,000,000 in
705 ms.

**The Solana failover ladder is zero-deep by default.** `setRpcFallback`
(`engine.ts:313`) returns `''` without a Helius key, and is direction-blind:
roughly 14 call sites pass `s.rpc.httpUrl` directly and never fail over even
when a key is present, contradicting the comment above them. There is
`extraWssUrls: string[]` but only one `httpUrl`. publicnode is the obvious
second endpoint and would silently break holdings and sell sizing — it refuses
`getTokenAccountsByOwner`, `getTokenSupply` and `getTokenLargestAccounts` with
*"Indexed requests require a personal token"*.

## 6. Feeds

- **Volume moved from the pump curve to pAMM.** pump logs are now 0.95 GB/h
  (the "780k pushes/h" note is 350k/h today); **pAMM is 9.7–12.5 GB/h, ~4M

  has **no UI to disable it** (`grep blockFeed src/` finds nothing), and by
  design produces zero used events while pump still emits logs.
- `priorityFeed`'s reconnect is the only one without jitter.

## 7. Terms and obligations

**Clean and worth keeping:** no shared API key is shipped. No key literals, no
`.env`, every credential read from user settings.

- **Jupiter §8.4 requires displaying "Powered by Jupiter".** Not present
  anywhere. This one uses obligation wording.
- **GeckoTerminal asks, but does not require:** *"We appreciate a link
  attribution back to GeckoTerminal because it helps us to continue providing
  the API for free."* **[C]** Correctly flagged and correctly *not* promoted to
  a violation.
- **`lite-api.jup.ag` is being retired** — Jupiter's migration doc says its
  limit "will be reduced progressively until it is fully retired". It is
  hardcoded, it is the app's most-called market host, and it is on the trade
  path. `MIN_GAP_MS.jupiter = 120` permits ~8 rps; the successor is 0.5 rps
  keyless, 1 rps with a free key, and there is **no `jupiter` entry in
  `WINDOW_LIMIT` at all**. That is a cliff, not a limit.
- **[C] The privacy policy undercounts what leaves the machine.**
  `shared/legal/documents.ts:228` is hash-pinned and user-accepted. Its market
  line names five hosts; missing are `lite-api.jup.ag` (the most-called),
  `api.rugcheck.xyz`, and `bsc-dataseed.bnbchain.org` — the BNB receipts host
  that exists *because* the listed publicnode refuses receipts, so it is
  contacted routinely. GIF hosts are unlisted too.
- **Birdeye's 30,000 CU/month is spent with zero accounting.** The full meter
  machinery exists for Helius (`shared/credits.ts`, `heliusBudget.ts`,
  `CreditMeter.tsx`) and Birdeye is not wired in. At ~35 CU per holder lookup
  that is under ~900 lookups a month, and the only symptom is a blank panel.
- **Unresolved, flagged for a human:** pump.fun's terms §21.h prohibits bots
  while §6.1 permits them. Not a question for an agent to decide.

## 8. What holds

Worth recording, because it was tested rather than assumed: no stampede when a
park releases (slow-start measured at 2× gap); the 20 s queue cap; `Retry-After`
clamping; Discover, watchlist and chart all serve stale data *with a note*;
portfolio honest nulls; the loss guard fails closed; and **exits are never
blocked, only delayed** — bounded park wait, ungated broadcast, sell retry and
order re-arm all intact.

## 8b. One open decision for the product owner, not a bug

`blockFeed` defaults to **true** (`shared/types.ts:855`), dials immediately
rather than on silence (`engine.ts:921` → `feed.ts BlockFeedSocket`), was
measured on 2026-09-09 at **5.51 GB/h** against the 1.5–3 GB/h its own comment
claims, and `grep blockFeed src/` finds **nothing** — there is no way for a user
to turn it off.

By design it produces zero used events while pump still emits logs, which it
does today at 99.9% reliability. So every user is currently paying about
5.5 GB an hour for insurance that has never yet been needed.

Three ways to resolve it, and the choice is a product one:

1. **Default it off, add a toggle.** Saves the bandwidth now. Costs the
   insurance: if pump's log emission drifts, the feed goes dark until someone
   notices and switches it on.
2. **Make it a true standby** — arm it but only dial after the log feed has
   been quiet for some window. Keeps both properties; more work, and it needs a
   silence threshold nobody has measured yet.
3. **Leave it on, add the toggle and tell the truth about the cost.** Cheapest
   honest option.

Option 2 is what the name "standby" already implies and is probably right, but
it is not a defect fix and should not be made on an agent's judgement. Flagged.

## 9. What shipped (all of it, 2026-09-09)

Every item on the fix order below is done. `npm test` is **90 suites**, both
typecheck projects are clean, `npm run build` succeeds and `npm run test:sandbox`
passes. Each lane proved its own tests by patching the built bundle back to the
pre-fix behaviour, running, and restoring — a test that passes either way pins
nothing, and several were caught doing exactly that during the work.

**Measured before and after**, from a harness that bundles the real modules and
counts requests against a stubbed fetch:

| Scenario | Before | After |
| --- | --- | --- |
| Idle Discover, pump.fun | **99/min** (limit is 60) | **26/min** |
| — `/coins/{mint}` re-buys | 44/min | **0** |
| — `/coins?creator=` per row | 44/min | **0** |
| — the New column's own feed | 11/min, starved | 26/min, its configured rate |
| 60-mint portfolio build | 209 requests | **130** |
| — DexScreener | 60 per-mint | **3 batched** |
| — Jupiter re-fetches | 26 | **0** |
| One token page | 14 requests, holder lookup ×2 | 12, ×1 |

pump.fun is back inside its published limit. The idle total fell less than the
pump number because freed budget went into work the app was already configured
to do: the New column now reaches its list feed every pass instead of every
other one.

**Correctness, not just capacity:**

- An unreadable mint no longer scores a safety PASS.
- The token page no longer asserts "no trading pool" or "no price" while the
  providers that would answer are parked — it says which are parked and that
  the app could not ask.
- A BNB sell whose block is pruned everywhere is unknown, never zero.
- A Cloudflare challenge no longer bans a working key, on reads or on sends.
- Both key-redaction gaps are closed, header-borne and query-borne.

**Two things deliberately NOT done, and why.** The block-feed default is a
bandwidth-versus-insurance tradeoff for the product owner (§8b). And `TTL_TOKEN`
was left at 8 s rather than lengthened — stretching a cache to hide a
re-fetch would make the answer staler to fit the bug; the batching was
restructured instead.

**Left open, named so it is not lost:** `getMultipleAccounts` would collapse the
remaining 60 `getAccountInfo` calls in a portfolio build into a handful, and
needs a `mintFactsMany()` in `onchain.ts`. Nothing subscribes to the new EVM
`wsEndpoint()` yet. `pumpswap` has no `WINDOW_LIMIT` entry and is now the
heaviest provider on an idle Discover, but no measured ceiling exists to set one
from — so none was invented.

## 10. Fix order (all complete)

1. **Response validators before the `res.ok` branch** — one hook, closes five
   P1s across both rails.
2. **Delete `checked: true` on the not-found branch** in `onchain.ts:84` — one
   line, stops an unreadable mint scoring safe.
3. **Park `host#method`, not `host`**, and seed the limiter from
   `x-ratelimit-method-*` — stops one dead holder lookup blinding the app, and
   unlocks the 30× headroom on cheap methods.
4. **Fix `PUBLIC_SUB_CAP`** — it is a connection cap, not a subscription cap.
   Ship before anything that adds subscriptions.
5. **Stop re-buying pump.fun rows** (`coinForIntel`, `buildRug`) — frees ~79
   calls/min and gets back under a published limit.
6. **Jupiter key field and host switch** — off a retiring endpoint, double the
   ceiling, and add the missing `WINDOW_LIMIT` entry.
7. **Per-capability EVM endpoint map** replacing the single `receiptRpc` —
   fixes all three BNB P1s and gives WSS somewhere to live.
8. **Correct the privacy policy host list** and add "Powered by Jupiter".
9. Batch routes: DexScreener 30-mint, `getMultipleAccounts`, GeckoTerminal
   `simple/token_price`.
10. Visibility gate on Discover; age-bound every remembered price.
