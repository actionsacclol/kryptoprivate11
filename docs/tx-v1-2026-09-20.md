# Transaction v1 broke every transaction read (2026-09-20)

## The report

A user following two active wallets saw the watcher count their leader's
transactions and copy none of them. The Console said, per transaction:

> Transaction version (1) is not supported by the requesting client. Please
> try the request again with the following configuration parameter:
> "maxSupportedTransactionVersion": 1. That trade was not copied.

Their diagnosis was right: the socket delivers the signature, the follow-up
`getTransaction` is refused. They also had ~30 copy positions still open that
the leader had already closed — the sells were refused the same way.

## What changed on chain

Solana **transaction v1** (SIMD-0385) activated on mainnet at epoch 1035 on
**2026-09-15**. Wallets and routers started emitting it within days; both
reported leaders' recent transactions are a mix of v0 and v1. An RPC refuses
to return a v1 transaction (error -32015) unless the request says
`maxSupportedTransactionVersion: 1`. The app said `0` everywhere (v0 was the
newest format when the client was written).

Verified against mainnet on 2026-09-20 with the public RPC: the leader's
transaction `4F3Fiyj…` is `version: 1`; the same request with `1` returns it,
and v0 transactions still return under `1`.

## What it broke

Every reader of a transaction, not just copy trading:

| path | what was lost while the leader/target used v1 |
| --- | --- |
| copy watcher (`walletWatcher`) | every leader swap → "not readable", not copied; leader sells not mirrored |
| block-feed standby (`feed.ts` blockSubscribe) | a block holding ANY v1 transaction is refused whole — most blocks, since 09-15 |
| fills (`priorityFeed.getTransactions`) | our own fills are v0 (we build MessageV0), unaffected today |
| ledger reconciliation, DBC/Raydium watchers, holder graph, decoder verify, template learner | any v1 transaction skipped silently |

## The fix

- `electron/chain/rpcClient.ts`: `MAX_SUPPORTED_TX_VERSION = 1`, used by
  `getTransaction`, `getTransactions` and the block subscription.
- `RawTransaction` gains the v1 fields (`transactionConfig` on the message,
  `version`, `signatures`). The JSON shape is otherwise the v0 shape — every
  reader (balance-delta swap decoder, `resolveAccountKeys`, the ledger) keeps
  working unchanged. v1 has no address lookup tables; `loadedAddresses` is
  empty and the resolver's concatenation is a no-op.
- `parseWireTransaction` (the base64 path on blockSubscribe) reads both
  formats. v1 on the wire, verified byte for byte against a mainnet
  transaction (`test/fixtures/v1-wire.json`):

  ```
  0      0x81
  1..3   header (numRequiredSignatures, numReadonlySigned, numReadonlyUnsigned)
  4..7   config mask, u32 LE
  8..39  recent blockhash
  40     number of instructions (u8)
  41     number of static account keys (u8, ≤ 64, no lookup tables)
  42..   keys × 32
  ...    config values (priority fee u64, compute unit limit u32, loaded
         accounts data size u32 — read as u32s after the keys: 52815, 0,
         89467, 13631488 matched the JSON), instructions
  tail   signatures × 64, signer order
  ```

  Only the keys and the first signature are read, as before.
- Copy status now counts the stages separately, as the reporter suggested:
  `seen` (socket), `swaps` (decoded and acted on), `notSwap` (read, not a
  swap), **`unreadable`** (seen, never returned by the RPC). The wallet's
  status line on the Wallets page shows "N unreadable" in red when it is
  non-zero, so a trade that disappears between the socket and the RPC is
  visible without opening the Console.

## Found on the way: base58 of an all-zero key

Pinning the v1 wire parse against the JSON showed one key that never
matched: the system program. `base58Encode` emitted its seed digit after
the leading-zero ones, so 32 zero bytes came out as **33** ones. Anywhere an
encoded key met the `'111…1'` constant (32 ones) it could not match, and a
PDA derived from that string used a 33-byte seed. Concretely: a PumpSwap
pool whose `coin_creator` is the system program (a coin with no creator
fee) had its creator-vault authority derived from the wrong seed. Fixed in
`electron/chain/base58.ts`; vectors pinned in `test/addresses.test.mjs`.

## Tests

- `test/txversion.test.mjs`: every transaction read in `electron/` goes
  through `MAX_SUPPORTED_TX_VERSION` and it is 1; `parseWireTransaction`
  reads the v1 fixture to the same signature and keys the JSON carries, and
  still reads a legacy wire; the v1 fixture decodes through
  `decodeWalletSwap` (the leader's own v1 trade).
- `test/walletwatcher.test.mjs`: the watcher's `getTransaction` carries
  `maxSupportedTransactionVersion: 1`.
- `test/feed.test.mjs`: the v0 wire path is unchanged.

## What the reporter should know

- Update to the build with this fix; nothing to configure.
- The ~30 positions the leader already closed will not close themselves: the
  watcher's catch-up only reaches back 30 minutes, and those sells are older.
  Close them from the Wallets page (sell) — the 90 s balance sweep flags the
  leftovers.
- Their suggestion to log seen → fetched → decoded → acted separately is now
  the status line.

## Reading from other RPCs

`getSignaturesForAddress` never inspects bodies and is unaffected.
Geyser/Yellowstone consumers need plugin 15.1.1+; this app has none.
