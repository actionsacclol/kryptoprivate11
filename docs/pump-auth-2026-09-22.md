# Signing into pump.fun with a wallet — 2026-09-22

The goal is a pump.fun account the app holds, so the terminal can act there:
callouts, the coin page, creator rewards, and a signed-in state the Links
widget can use.

The sign-in works, verified against the live endpoint. What is missing is the
user interface and everything downstream of holding a session.

## What was verified against the live endpoint

| Fact | How |
|---|---|
| `POST /auth/login` exists | Empty body answers 401 `{"message":"Invalid signature"}` |
| Body is `{ address, signature, timestamp }` | Their own schema, plus two independent public write-ups |
| Optional `transaction`, `authType`, `deviceId`, `rawJwt` | Their schema |
| `authType` accepts `non_custodial` | Their schema — this is us, and it means no Privy layer is required |
| Signature ≤ 88 chars, address ≤ 44 | Their schema; 88 chars is a base58 ed25519 signature |
| Three login routes | `/auth/login` (cookie, or raw token with `rawJwt`), `/auth/login/token` (bearer), `/auth/login/session` (cookie, 400 without an Origin header) |
| Rate limit 50 / 60 s | Response headers |
| No published schema | Five doc paths 404, one 403 |

`/auth/login/token` was then confirmed working with a real signature — see
below.

## The message, and how it was settled

```
Sign in to pump.fun: 1790047569405
```

Read off a real sign-in on 2026-09-22 — the text Phantom itself displayed
before signing. Thirteen digits, so **milliseconds**. One space after the
colon, capital S, no trailing punctuation.

It could not have been derived. A wrong message and a wrong key are answered
identically ("Invalid signature"), and it appears in no published schema.

Then confirmed end to end: a throwaway keypair generated locally, signing
exactly that string, was accepted by `POST /auth/login/token` with a 200 and a
bearer JWT. So the template, the unit, the route and the envelope are all
verified against the live endpoint rather than assumed.

**Route choice.** Their own site uses `/auth/login/session`, which sets a cookie
and refuses without an `Origin` header — sensible for a browser, wrong for a
desktop app with no origin to honestly claim. This app asks for the bearer arm
and carries the token itself. `/auth/login` with `rawJwt: true` returns the same
token and is kept as a fallback, because their schema calls the original
superseded and a superseded route is the kind that eventually 404s. A 401 is
never retried on the other arm: it means the signature was rejected, which
both arms would do identically.

## The security property, and why it is a shape rather than a check

Every signing path in this app is a named door with its own intent: a trade, a
fan-out buy, a launch that additionally demands the freshly generated mint
secret. A login message is not a transaction, so none of `checkOutflow`'s
validation applies to it — which makes it exactly the shape that must never
become a general "sign these bytes" call. That primitive is what wallet
phishing is built on, and here it would sit beside keys holding real positions.

So `wallet.signPumpLogin(walletId, timestamp)` takes a string and a **number**.
The message is built inside the door from the shared template. There is no
parameter through which caller-supplied bytes can reach a signature. The test
asserts the parameter list literally, and that `ed25519.sign` appears in
exactly one place in the whole app.

The rest follows the same discipline as `launchMeta.ts`: the host is a
constant, nothing takes a URL or path component from a caller, and both
requests refuse redirects, because a 30x to a private address is the classic
way out of an allowlist.

## Sessions: one account per wallet

pump ties an account to the address that signed in, so three wallets are three
accounts and all three are valid at once. Sessions are held in a map keyed by
wallet id, and every call that acts as an account NAMES the wallet it acts for.

There is deliberately **no separate "active pump account" setting**. The app
already has exactly one idea of which wallet is acting, and a second pointer
chosen independently is a thing that drifts out of step and posts as the wrong
account. The session simply follows the wallet.

Stored at `userData/pump-session.json`, each token **encrypted at rest**
through the same `safeStorage` the wallet secrets use. Where OS encryption is
unavailable a token is not persisted at all rather than written in the clear;
the session works for that run and the user signs in again next time. The field
is named `token`, which `system/diagnostics.ts` already treats as a secret, so
the support bundle redacts it.

No token crosses IPC. Sessions leave main only through `viewOf`, which strips
the credential, and `token(walletId)` is main-only and names its wallet so a
caller cannot act as the wrong account by accident.

An unreadable store, or one whose tokens will not decrypt on this machine, is
reported rather than silently treated as "never signed in" — the same rule the
2026-09-09 fail-open audit applied to five other modules. The loader also reads
the single-session shape this file had for one day, so nothing is dropped.

`test/pumpsession.test.mjs` runs all of that against a temp directory: three
accounts at once, each token to its own wallet, nothing in the clear on disk,
every account surviving a restart, signing one out leaving the others alone,
signing in again refreshing rather than duplicating, and both failure modes
reporting themselves.

## Where it lives

**Wallet page → pump.fun accounts**, under the wallet list and above Backup. It
is there rather than on the Launch page because the account *is* the wallet, and
that page is where someone looks at what their wallets are and what they can do.

One row per Solana wallet: its label, whether it is the trading wallet, and
either the pump account (display name once their profile read answers, else the
address) or "No account yet". A wallet with no session is offered **Create
account**, not "Sign in" — pump has no separate registration step, so signing in
with a new address *is* the creation, and asking someone to sign in to an
account they do not have would be asking for something that does not exist. A
signed-in wallet gets Refresh, which re-signs and is how a two-week session is
renewed, and Sign out, which names its wallet so one account can go without
taking the others.

When the build cannot sign in — the message template no longer matching — the
section says so and disables the buttons rather than offering something that
would be refused at pump's end.

## What is not built yet

- **The Links widget has no signed-in state yet.** The sessions exist; nothing
  downstream reads them.
- **Nothing that uses the session.** Posting a callout, reading eligibility,
  the Links widget's signed-in state: all of that is downstream of having a
  session at all.
- **`/callout/eligibility/{mint}`** answered 401 when the callouts rail was
  built on 2026-09-18. It should be readable now that a session exists, and it
  is the first thing worth checking — it tells us what a coin needs to be
  callable, and whether posting a callout is reachable at all.

## The profile: username, bio, picture

Signing in creates the account. It does not give it a name — a fresh account
has no username, no bio and no picture, and the row shows its address because
that is what is honestly known about it.

Wallet page → pump.fun accounts → **Edit profile**, inline under the account's
own row. Not a modal: with five accounts the one thing a dialog would fail to
make obvious is *whose* profile is being edited.

### The route, all of it observed

Captured 2026-09-22 from a real profile edit, because the field names are not
guessable and probing does not find them:

```
POST frontend-api-v3.pump.fun/users   →  201 Created

{ "username": "kryptobottest" }                          28 bytes
{ "bio": "bio test" }
{ "profileImage": "https://ipfs.io/ipfs/bafkrei…" }      99 bytes
```

**Three requests, one field each.** That is what their client does, and the
byte counts prove it — 99 is exactly that one key and that one value. One
request carrying all three is probably fine; "probably" is not what gets sent
at somebody's public profile, so `profileUpdates` produces one body per changed
field and the sender posts them in turn, stopping at the first refusal. A
username pump rejects as taken is the common case, and carrying on to write the
bio would leave the account half-edited with no account of what landed.

**Only changed fields are sent.** The diff is taken in main against a fresh
read of what pump holds, not against what the form was showing when it opened —
otherwise a bio edited on pump.fun itself gets overwritten by a stale form. A
field *cleared* counts as a change: that is somebody deleting their bio.

**Auth is the cookie**, the same as callouts: their preflight answers
`access-control-allow-headers: content-type`, so a browser cannot send an
Authorization header. This app sends the cookie and a bearer both.

**Rate limit**, from the response headers: `x-ratelimit-limit: 30`,
`x-ratelimit-reset: 120`. Three fields across five accounts is fifteen writes,
so there is no queue here — only the knowledge that the limit exists.

### The picture is a URL, not an upload

`profileImage` points at an already-hosted image, and the link pump's own
client sent is an `https://ipfs.io/ipfs/<cid>` gateway URL — the same shape the
launcher's pinning already returns. So choosing a file pins it through
`pump.fun/api/ipfs` (`uploadProfileImage`) and the resulting link is what gets
written. The unused metadata JSON that upload also pins is the price of not
sending a second, untested request shape at the same host.

It is pinned when the file is chosen, not when Save is pressed, so the link is
real before anyone presses a button that writes a public profile.

**Showing it goes through the app's own image handler** (`krypt-img://`, the
one token icons use). `img-src` does not allow `https:` on purpose: a remote
host must not learn this install's IP from a picture. A raw `<img src={url}>`
would have been blocked by the CSP, and would have been wrong even if it were
not.

### What is pump's to say

Whether a username is taken, long enough, or allowed at all. The app caps the
two text fields at 64 and 512 so nothing absurd is sent, refuses a picture that
is not an https link, and otherwise shows pump's refusal in pump's words. Those
caps are not a guess at their rules — their rules are not known.

### Pinned by

`test/pumpprofile.test.mjs` — 8 checks, including the two captured byte counts,
that a partial edit stays partial, that the picture link is not cut to a
username's length, and that the renderer names no host and no file path.

## Existing accounts (added 2026-09-22, evening)

An imported wallet that already has a pump.fun account logs in to THAT account
when it signs in — pump ties the account to the address. So bringing an
existing account = importing its key + signing in; nothing is created.

To tell the two apart before signing, pump's PUBLIC profile read (observed live):

    GET https://frontend-api-v3.pump.fun/users/<address>     (no auth, 30 / 60 s)
    404 {"message":"User not found"}          → no account; signing in creates one
    200 {..., "is_pump_user": true,  username, followers, is_banned}  → real account
    200 {..., "is_pump_user": false, username: "lateoctopus4697"}     → pump's own
        auto-made record (the system program has one); nobody has signed in

Anything else is `unknown`, never "none". `accountLookupFrom` in
shared/pumpProfile.ts, `lookupAccount` (10-min cache, cleared on sign-out) in
electron/system/pumpProfile.ts, IPC `pump:lookup(walletIds)` and
`pump:importAccount(secret, label)` (reuses `wallet.importSecret`).

UI: the Wallet page rows say "Has @name · N followers" with **Sign in** (only a
404 address gets **Create account**); the pump.fun accounts page has **Bring an
existing account** (paste key → import + sign in → offers "Make it the trading
wallet", because auto-callout posts from the trading wallet's account) and an
**Already on pump.fun** list above **Accounts to make**.
